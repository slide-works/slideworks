Live polls: ask the room, watch the bars move

A poll is a slide. The presenter reaches it, the phones that joined in SW-5 swap the slide mirror for the question, and the bars on the big screen grow as answers arrive. This page mocks all three screens: the guest phone, the big screen and the presenter window from SW-4. The live demo runs a whole poll, and you can answer on the phone yourself. The eight questions at the end were answered on 17 Nov (D1–D8).

01

What SW-6 ships

In SW-6

  • A poll slide layout: a question, 2 to 8 options and result bars
  • Two ways to answer: pick one, or pick up to N. Either can mark a correct answer
  • The poll card on the guest phone, which fills the activity slot SW-5 left empty: pick, send, see your answer, change it
  • Live bars on the big screen, pushed over the SW-5 audience channel, with an answer count
  • A results setting per poll: live, after you've answered, or after the poll closes
  • Presenter controls in the SW-4 presenter window and phone remote: open, close, reveal, new round. Every later question type reuses them
  • MCP tools so an agent can write a poll, change it and read what the room said
  • A load run at 1,000 voters (Q8)

Later Features

  • SW-10 scales, ranking and 100 points, on the same poll model
  • SW-8/9 word clouds, Q&A, and options the audience suggests
  • later donut and pie results; SW-6 draws bars only
  • SW-11 quiz scores, nicknames and leaderboards; SW-6 only says whether you got it
  • later exporting answers to a file

On the big screen

The poll layout draws the question, one bar per option and a footer with the state and the answer count. The join pill, top right, is always on a poll slide while the deck is live, so a latecomer can still get in. Bars use the palette's accent, so a poll looks like the rest of the deck.

The poll model

The shape follows the voting service in the earlier prototype (SW-1 reuse review, section 2): a poll has a method, a method config, options and a lifecycle. SW-6 builds two methods. SW-10 adds rating, ranking and budgets as new methods on the same tables, screens and controls.

Rules
  • One answer per guest per round. Sending again replaces the whole answer. Each answer has a revision number, and a send against an old one is refused.
  • Opening freezes the method, the max, the privacy and the results setting. The question and option text can still be fixed for a typo.
  • Hidden means hidden. While results are hidden, the counts never reach a guest's browser, so nobody can read them in dev tools.
  • Each Go live is a clean slate. Answers belong to the session (SW-5 D4), then to a round within it.
  • 2 to 8 options, each up to 60 characters, and a question up to 120. Past that the bars stop fitting the canvas.
  • Late joiners get the open poll straight away. If it has closed, they see the result.
Privacy
  • Private (the default): an answer is stored against the random guest ID from SW-5, which has no name. The presenter and agents see totals only. No screen or tool lists who picked what.
  • Named: the voter is told before answering and gives a name. SW-5 has no names (D2), so this needs the nickname step that a quiz would also need. I'd leave it to the quiz Feature, SW-11 (Q5).
  • Deleted together: ending a session keeps its answers. Deleting the session or the deck deletes them.
Measure
  • Response rate per poll: people who answered ÷ guests joined when the poll closed. The presenter panel shows it live (93% of 41).

Agents write and read polls over MCP

Because a poll is a slide layout (Q1), an agent adds one with the tools it already has. The question and options are slots. Five new tools cover settings, running a poll and reading the result.

you After slide 3, ask how big their last merge request was. Four size bands. agent add_slide(after: 3, layout: "poll", slots: { question: "How big was your last merge request?", options: ["Under 50 lines", "50 to 200 lines", "200 to 1,000 lines", "Over 1,000 lines"] }) → slide 4 · poll · Draft · pick one · results live you Hide the results until I close it. agent update_poll(slide: 4, { results: "after_close" }) → ok … after the talk … you What did the room say? agent get_poll_results(slide: 4) → 17 Nov session · round 1 · 38 of 41 answered 50 to 200 lines 45% · 200 to 1,000 lines 26% Under 50 lines 18% · Over 1,000 lines 11%
ToolDoes
add_slide · update_slideExisting tools. Layout poll with slots question and options. list_layouts describes it.
update_pollSettings: pick (one, up_to), max, results, correct, opens (on_arrival, manual). Refused while the poll is open.
add_poll_optionAdds one option without resending the list. Allowed while open: it appears on phones at once, and nobody's answer changes.
open_poll · close_pollThe presenter's buttons, for an agent acting as co-pilot. They work only while the deck is live.
get_poll_resultsTotals per session and round, with the response rate. Never who picked what.
08

Realtime and load

SW-5 already sends every guest an audienceState with an activity field that is always null. SW-6 fills it. Answers go up over plain HTTP, so they work on every transport fallback and a refusal is an ordinary 409. Results come down as a tally pushed at most twice a second, however many answers arrive. The prototype polled every 15 seconds; this pushes.

MessageCarries
audienceState.activityHub → guests. { type: "poll", slide, phase, round, pick, max, options, results }. Null on a slide with no poll, as in SW-5. A reconnect lands on the current one.
PUT …/answerGuest → server, over HTTP. { round, picks, revision }. Returns the new revision, or 409 with the current poll state when the round or revision is stale or the poll has closed.
pollTallyHub → big screen and phones. { round, answered, counts }. counts is null while results are hidden from the room.
pollTally (watch)Hub → the owner's presenter window and remote. Always with counts, plus the response rate.
open · close · reveal · show answer · new roundOwner → server, over HTTP. The same owner check as Go live.
Load targets (from the prototype's harness)
1,000 votersmust pass in SW-6
3,000 votersmeasured, recorded
10,000 votersmeasured, recorded
  • Everyone answers within 30 seconds of the poll opening
  • Sending an answer: p95 under 1 s. Results on screen: p95 under 2 s after the answer
  • Errors under 1%

The risk to plan for: SlideWorks runs on SQLite, which has one writer. A thousand answers in a few seconds have to be queued and written in batches, not one transaction each. The 1,000-voter run is there to prove that works.

Questions before planning

Answered 17 Nov. Q1, Q2 and Q4 to Q8 went as recommended. Q3 changed: a tap sends for pick-one, and Send stays only where several picks are needed. The phone mockups and the demo above now work that way. All eight are recorded as decisions D1–D8 on SW-6.

Q1 · Where does a poll live in a deck?

This decides how an agent creates one and what later question types plug into.

Not queued

Q2 · When does a poll open and close?

Every button the presenter has to remember mid-talk is a chance to stand in front of a room with a poll nobody can answer.

Not queued

Q3 · Does a tap send the answer?

SW-5 got joining down to zero taps. Here it's a choice between the fewest taps and one pattern for every question type.

Not queued

Q4 · Which results setting is the default?

All three ship. Most polls will never have the setting touched, so the default is what people get.

Not queued

Q5 · Do named polls ship in SW-6?

The Feature lists private and named. Named needs guests to have names, and SW-5 decided they don't (D2), leaving nicknames to the first activity that needs them.

Not queued

Q6 · How is a correct answer shown?

The Feature has "optional correct answer". This is the edge of quiz territory.

Not queued

Q7 · What does resetting a poll do?

Asking the same question at the start and the end of a talk is a common move. The Feature calls reset "a new round".

Not queued

Q8 · Load target and measure

The Feature says "load target to agree" and "measure to confirm". SlideWorks is self-hosted on SQLite, so the first target should be one a single instance can honestly meet.
