Custom template upload

A person or an agent makes their own template: fonts, logos, title art, ornament, a palette and, later, custom layouts. It is checked, published and shared like a deck. The example brand, Northwind, is made up. Importing a look from an existing deck is now a separate Feature, SW-354. The built-in layout gaps found rebuilding a real deck (was SW-355) are merged into SW-50 and are not mocked here yet.

The split, and what SW-50 ships

SW-50 used to cover two things. It is now only the template itself. Reading a look out of an existing deck moved to SW-354, which produces a draft that opens in this Feature's editor.

SW-50 Custom template upload

  • A template editor in the app, starting from a built-in template
  • Fonts (woff2), logos for light and dark slides, title art, ornament dots
  • Its own palette, contrast-checked, optionally locked, with a second accent and up to four extra colours
  • Draft, publish checklist, publish; archive instead of delete
  • Versions: a deck stays on the version it was made with and is offered the update
  • Templates page; sharing like a deck
  • MCP: create_template, update_template, get_template, publish_template, upload_asset
  • Last wave: custom layouts as HTML with typed slots, which can react to numbers, choices and clicks

SW-354 Deck import (new Feature)

  • import_template and "Import from a deck…"
  • Reads an HTML deck: colours, logos, font names, known art
  • The import report: mapped, adjusted, needs files, needs review, dropped
  • PowerPoint (.pptx, .potx) later
  • Open there: whether slides come in too

Comes after SW-50. Its output is an SW-50 draft template.

Today What SW-2 already built

  • The Template record already has type, shape, titleArt, ornament, logo, palette and lockPalette
  • Three built-in templates, four palettes, from JSON files
  • The contrast check that fails a bad palette
  • One raster logo per deck, in the footer
  • Not drawn on slides yet: title art and ornament colours

Checks, and what each failure looks like

A file that fails a check is refused at upload with the reason. Checks that depend on several fields show in the publish checklist. The same texts go back to an agent as the tool's error.

Not a woff2 file

NorthwindSans-Bold.ttf
refused
Fonts must be woff2 files. This one is TrueType.

Checked by the file's first bytes, not its name. Other formats are refused, not converted.

Font too wide or too narrow

northwind-display-900.woff2width 0.74 em
refused
This font is too wide for slide text (0.74 em; the limit is 0.70).

The server measures a sample line in headless Chromium. Inside the limits, the measured width replaces the built-in 0.56 em when slides are checked for fit (Q5).

Rights not confirmed

Publishing is blocked. An agent can't confirm this: publish_template returns the reason and the editor's link for a person to open.

The same bars as the built-in palettes (SW-2). The editor offers the nearest colour that passes. It never changes a colour by itself.

Unsafe SVG

logo.svg
refused
This SVG contains a script. Export it again without scripts, or upload a PNG.

Scripts, event handlers, foreignObject and links to other files are refused, not stripped silently (Q3).

04

Custom layouts

last wave of SW-50 (Q2)

A custom layout is defined the way a built-in one is: a name, a description for agents, and typed slots. The difference is that its markup is uploaded. It is parsed into a checked tree on the server and drawn from that tree, so no uploaded HTML string ever reaches a page. The markup can react to slot values in three ways: a number sets a length or an angle, a choice picks a variant, and an element can wait for a later click.

Three ways the markup reacts to a slide's values

BindingIn the markupWhat it is for
A number sets a CSS variabledata-var="--v: share", then width: calc(var(--v) * 1%)Bar lengths, a gauge needle's angle, a marker's position. The slot declares its range, so the value can't push anything off the slide.
A choice picks a variantdata-variant="state" adds .is-goalA highlighted rung, an alert bar, a struck-through row. Only the values the slot lists become classes.
An element waits for a clickdata-step, or data-step="2"Reveals, the same as built-in layouts: hidden steps keep their space, and the presenter's step count includes them.
Light or dark"surface": "either" in the slots fileThe slide chooses. On dark, tokens resolve to the night colours, and both are contrast-checked.
MotionNone yetBars that grow and needles that swing are a later story, with a few named effects SlideWorks owns.
bottleneck-barsTwo numbers set the bar lengths, a third the dashed outline; state: alert turns a bar red. The dark note uses the extra colour "Stage".

Allowed

  • Tags: div, span, p, h2, h3, ul, ol, li, b, i, em, strong, and svg shapes without text or links
  • Attributes: class, data-slot, data-each, data-if, data-var, data-variant, data-step
  • Slot types: the ones built-in layouts use: text, number, enum, list, object, image, and the callout, chip and badge blocks
  • CSS: one <style> block with class selectors; layout, spacing, borders and type size; colours and fonts only as var(--sw-…), including the template's extra colours
  • Slot text is plain text, as everywhere else in SlideWorks

Refused, with the line it is on

  • <script>, event handlers, <iframe>, <form>, <a>, <img> outside an image slot
  • Hex, rgb(), named colours and font names: the same rule as the repo's own layouts
  • url(), @import, @font-face, position: fixed, animation and transitions (motion comes later, as named effects)
  • Selectors that reach outside the layout: element selectors, :root, .sw-… classes
  • Text written in the markup. Every word on a slide comes from a slot, so agents and lint can see it

How we build it

checked against main at 21160cc

Most of the model exists. The work is in five places: a store for templates and their files, a catalogue that knows who is asking, the checks, drawing the new parts on slides, and the screens.

Blue is new. Orange exists and changes.

What changes, and where

PieceTodayFor SW-50
Where templates come fromITemplateCatalogue is a singleton over the embedded templates.json, injected into about 14 classes. It has no idea who is asking.The catalogue also reads the database. Find(name) returns any template so a deck always renders. A new ListFor(actor) returns what the caller may pick. GET /api/looks stops being the same for everyone.
What a deck storesDeck.Template and Deck.Palette are names.The names stay, and a deck also stores the template version it is on. An uploaded template's short name is unique across the server and can't clash with a built-in. Built-ins have no versions, so no existing deck row needs more than a default. A template's palette is stored inside each version.
FilesImageStore keeps images per deck: 10 MB, PNG, JPEG, WebP, GIF. SVG is refused.A template asset store beside it, with font, logo, art and layout kinds, and the same one-time upload URL. Files are kept under ids and never replaced in place, so a URL can be cached for good and every published version keeps its own files.
FontsInter and Plus Jakarta Sans are bundled. lookStyle.ts sets families by name.The look carries a list of font files. The slide adds one @font-face per file, under a family name unique to the template. The share card and preview_deck wait for fonts before the screenshot.

Risks

  • Font licences. A woff2 sent to a browser can be saved by any viewer. The rights tick, the name and time recorded, and serving fonts only for decks on the template are what we can do. Worth one line in the docs for server owners.
  • The catalogue seam touches about 14 classes, and SW-9 is being built on the same files now. Wave 0 should land it small and early.
  • SVG. Allowed today nowhere. A sanitiser is new code on a security boundary; it needs its own hostile-file tests.
  • Custom layouts are the largest and least certain part. CSS that passes the allow-list can still be ugly or fragile. That is why they are last and why each is looked at before publishing.
  • A rebrand takes a click per deck. Decks don't follow the template by themselves. "Update my decks" covers the owner's own; decks other people made stay on the old version until they update.
  • Disk. Every published version keeps its files for good. A file unchanged between versions is stored once. The limits in section 03 cap it per person.

Q1 · How does a person make a custom template?

The Feature is called "upload", but a template is about 15 fields and up to a dozen files.

Not queued

Q2 · When are custom layouts built?

They are the largest and least certain part: a sanitiser, a new renderer, fit checks and a review screen. Everything else is useful without them.

Not queued

Q3 · Which file types can a logo or title art be?

Brand logos are almost always SVG. SlideWorks refuses SVG today because an SVG can carry script.

Not queued

Q4 · What happens to decks when a published template is edited?

A logo refresh should reach every deck. A half-finished edit should reach none.

Not queued

Q5 · How does text fit work with an uploaded font?

The server refuses a slide whose text won't fit, and it assumes Inter and Plus Jakarta Sans (0.56 em a character). A wider brand font would overflow slides it accepted.

Not queued

Q6 · Who reviews a custom layout before it is published?

D1 says each layout is "reviewed by a person". The checker already stops scripts and outside styles, so the review is about whether the layout looks right and holds its content.

Not queued

Q7 · SW-50's Measure

The belief is that uploaded templates make decks match a house look without hand-written HTML.

Not queued
