A SlideWorks voice for languages the phone can't speak

SW-885 lets a guest listen to the translated talk through the phone's own voice. When the phone has no voice for the language, for example Android Chrome without a Thai voice pack, Listen can't start (SW-885 D13). SW-982 adds a fallback voice that SlideWorks runs itself: an open text-to-speech model where one exists. This page compares where that model could run, shows the guest screens and the admin tab, and ends with the decisions.

finding D13 can't always tell

On Android Chrome a listed voice may not be installed, so SW-885's no-voice check passes and the guest hears Thai lines read by an English voice. The sheet's Try is how a guest finds out. SW-982 gives them somewhere to go: the SlideWorks voice is one tap away in the same list (03, state 2).

finding The gap is the Asian languages

Thai, Malay, Vietnamese, Indonesian and Cantonese are the likely gaps, and Thai is a first speaker-and-guest language. These are also the languages with the fewest open voice models (07).

02

Where the voice runs

D1: A, the server

SW-982's goal named two places: the guest's device, or the SlideWorks server. The app can also run a model natively, so there are three. Numbers are from the research; ~ marks my estimates.

A On the SlideWorks server

How
One synthesis per line per language, in a voice container next to SW-943's translation containers. Guests fetch each line's audio.
Guest download
~6–27 KB a line (Opus at 24 kb/s) or a bit more as MP3. Nothing up front.
Server CPU
Piper-class voices use ~0.15–0.35 of a core to keep up with speech, per language with a listener.
Added delay
~0.3–1.5 s synthesis + one fetch.
  • Any phone, web or app, even with no voices at all.
  • 300 guests in Thai cost one synthesis, as with translation.
  • One voice for everyone; easy to swap models in config.
  • In the app, plain media audio fits the lock screen better than system TTS (see 06).
  • GPL voice code stays in its own container, out of the MIT app.
  • Server CPU, and a container self-hosters may skip.
  • Needs the network for every line.
Recommended.

B In the guest's browser

How
A WASM build (piper-tts-web or sherpa-onnx WASM) and a voice model, downloaded on first use and cached.
Guest download
~60–110 MB per language (sherpa-onnx's English demo is 12 MB of WASM + 97 MB of data).
Phone CPU
Piper runs at RTF 0.36–0.77 on a Raspberry Pi 4; a budget phone is in that range.
Added delay
The whole download before the first line, then ~0.5–2 s a line on a cheap phone.
  • No server cost; works on a self-hosted server with no extra container.
  • 40 Thai guests pull ~2.4 GB through venue Wi-Fi as the talk starts.
  • The phones that need it most are the slowest.
  • iOS kills WASM pages under memory pressure, and an open WebKit bug (304810) grows WASM memory until iOS 26 kills the page.
  • Piper's pronunciation step is GPL espeak-ng, shipped inside our MIT web bundle.
Not recommended.

C Native in the app

How
react-native-sherpa-onnx (MIT, Expo config plugin) with a VITS/Piper model per language.
Guest download
~60–75 MB per language, ideally before the talk.
Phone CPU
Native ONNX, faster than WASM; battery over an hour not measured.
Added delay
~0.3–1 s a line (~).
  • Works offline once downloaded.
  • No server cost.
  • App only: mobile web guests, the most common, still get nothing.
  • A second engine to build and test beside A or instead of it.
  • Needs an Expo development build (the app already needs one for SW-884).
Not now. Revisit if guests need offline listening.

Whichever place: the models don't cover the gap languages cleanly

I found no open voice with a clear commercial licence for Malay. Thai and Cantonese each have a candidate tagged MIT or Apache, but their training data is not stated. Vietnamese, Chinese, Japanese, Korean and the European languages are fine (07). So "a local model" alone can't close the Thai gap that started this Feature. Option A can, because its seam can also call a cloud voice for those languages: Azure covers all 15 plus Cantonese at about $15 per million characters, roughly $0.70 per language for an hour's talk (~). That is D3.

The app's audience mode

native app

The app has the same gap: Android's TextToSpeech has no voice until its voice data is installed, and some phones ship an engine with no Thai at all. The app offers the same SlideWorks voice. Server audio is plain media, so it fits the background audio and Now Playing that SW-885 already needs.

06

How a line becomes audio

Translation already happens once per line per language on the server (SW-943). The voice is the same idea: one synthesis per line per language, and only for languages where at least one guest is listening with the SlideWorks voice. Guests whose phone has a voice are unaffected.

Time behind Sam, per line (~)

Within the D9 budget: a line still plays well before the next one is usually final. If Sam talks fast, D9's skip applies as it does today. Synthesis is Piper-class at RTF 0.15–0.35 on one core for a 2–9 s line, less with threads; starting it the moment translation lands (not when the guest asks) hides most of it.

Venue Wi-Fi for 40 guests listening in Thai (~)

A Piper "medium" voice is 61–75 MB. Audio: a 2–9 s line is ~6–27 KB as Opus at 24 kb/s (Xiph), a little more as MP3.

Contracts (proposed, for the plan to confirm)

// guest → hub: SW-885's message gains the voice
SetListening({ listening: true, voice: "server" })   // or "phone"

// guest → server, per line it is about to play
GET /api/live/{code}/speech/{lang}/{seq}
  200 audio/mpeg   // ready, or synthesised now (single-flight)
  404              // no voice for {lang}: skip the line
  504              // slower than Speech:Timeout: skip the line

// server config, like SW-943's Translation:Models
Speech:Voices: [
  { id: "open",  adapter: "sherpa", endpoint: "http://voices:8080",
    languages: { vi: "vi_VN-vais1000-medium", id: "supertonic-3", … } },
  { id: "azure", adapter: "azure", region: "southeastasia",
    languages: { th: "th-TH-PremwadeeNeural", ms: "ms-MY-YasminNeural", yue: "zh-HK-HiuMaanNeural" } } ]

The server starts synthesising a language's lines as soon as they are translated, but only while that language has a guest with voice: "server". With nobody on it, nothing runs. A GET for a line not yet done waits on the same job rather than starting another.

Things to check during planning

  • Playback on web: play every line through one reused <audio> element started by the Start tap. Safari suspends Web Audio in the background, but an <audio> element keeps playing (WebKit 261554, 198277). Whether JS may start a new line while an iPhone is locked is unknown: test on a device before promising screen-off listening on web. D12's Wake Lock stays.
  • Re-arming: iOS can leave audio "interrupted" after a call or a focus change (WebKit 273511, 276016). Watch for it and show Resume, as D12 does.
  • Format: MP3 or AAC plays everywhere. Opus is smaller; check Safari before choosing it.
  • App, and a risk for SW-885: developers report AVSpeechSynthesizer pausing when the screen locks (Apple forum 849627). SW-885's locked-screen listening (D17) may need server-style audio played as media anyway. Check before SW-885 is planned.
  • Android voice check: treat a listed voice as unconfirmed. Count, per language and platform, how often guests switch from the phone voice to the SlideWorks voice after Try. That's the gap data nobody publishes.
  • Self-hosting: both engines are optional. With neither, SW-885 D13 is unchanged. docs/self-hosting.md gets a section.
  • Metrics: per call, engine, voice, language, characters, synthesis ms and outcome to VictoriaMetrics, as SW-943 does.

Ruled out

  • Meta MMS-TTS: covers th, vi, id, ms, ko, but the weights are CC-BY-NC.
  • XTTS-v2, F5-TTS: non-commercial weights. Coqui has shut down.
  • Kokoro-82M as a main voice: Apache, but no th/ms/vi/id/ko, and RTF 2.8–7.6 on a Pi 4.
  • Chatterbox multilingual (has ms): 500M, weights licence not stated, unmaintained.
  • Qwen3-TTS 0.6B: Apache, but no th/ms/vi/id/yue and GPU-class.
  • AWS Polly: no th, ms, vi or id.

Running them

sherpa-onnx (Apache-2.0) runs VITS/Piper, Supertonic, Kokoro and Matcha voices on CPU in one process, which suits one voice container. Piper's own runtime is now GPL-3.0 (OHF-Voice/piper1-gpl) and its pronunciation step uses GPL espeak-ng; in a separate container reached over HTTP, that stays out of SlideWorks' MIT code. Piper's Thai step (TLTK, Python) and MeloTTS need checking for whether they fit the same container.

Cost on CPU: Piper needs ~0.35 of a Ryzen 7 5700X core to keep up with speech (Picovoice), RTF ~0.15 on an i7-1255U. A 2–9 s line is ~0.3–3 s of one core before threading; the host's numbers decide the real figure.
