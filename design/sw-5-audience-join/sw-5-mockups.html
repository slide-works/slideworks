SW-5 · SlideWorks · mockups 17 Nov 2026

Audience join: scan, land, follow

Nearly everyone joins by pointing a phone camera at the screen, so the phone page is the product and the presenter's side is support. The goal is to go from QR to joined with zero taps after the camera, keep the phone in step with the presenter, and make it obvious that guests need no app and no account. The live demo below drives a phone from a presenter's laptop. Seven questions at the end need your call before planning.

01

What SW-5 ships

In SW-5

  • The presenter's Go live in the player opens a session with a 6-digit code and a join link
  • A join slide layout with a large QR code, the short link and the code, plus a joined count
  • An optional join bar (small QR + code) in the corner of every slide
  • A guest page for phones: no account, follows the current slide, shows a waiting state
  • A join domain, slideworks.live: the QR opens slideworks.live/482913, and the bare domain is the type-the-code page
  • The session channel on the existing SignalR deck hub, with no guest cap, which SW-6 to SW-11 build on
  • A privacy sheet on the phone that says what a guest leaves behind

Later Features

  • SW-6+ polls, word clouds and Q&A in the activity card (mocked here only as a placeholder)
  • later phone remote and speaker notes for the presenter (not the guest page)
  • later guests browsing back through past slides
  • never an app install or a guest sign-in

The 10-second journey

0 taps after the camera

Camera, then the browser, then you're in. There is no Join button, name field or cookie banner in the way. The page joins on load and says so. A guest who opens it before the talk starts lands in a lobby (see states).

Live demo: drive the phone from the laptop

Press Go live, then step through the deck. The phone follows. On the join slide the joined count ticks up. Slide 4 is an interactive slide, so the phone shows its activity card. Use the toggles to try the join bar, a dropped connection and ending the session.

Try
  • Go live sits in the player toolbar. It opens a session for this run of the deck. Ending it closes every phone.

04

Every phone state

One page, slideworks.live/{code}, with every state on it. The deck's palette colours the page, here the default Cobalt on the night surface, which reads well in a dark room. Targets are at least 48 px tall. Nothing scrolls sideways.

Type the codeslideworks.live with no code: the home page is the keypad. A numeric keypad (inputmode="numeric"). It joins as soon as the sixth digit is typed.
Wrong or ended codeSays what to check. It never shows a 404, and the digits stay so the guest can fix one.
Before Go liveThe code is known before the talk (Q4). Early joiners wait here, and the page moves on by itself.
FollowingThe slide mirror with a progress strip. The card below it says there is nothing to answer yet.
ReconnectingThe last slide stays on screen. An amber banner shows, and the page catches up silently when the connection is back.
Privacy sheetOpens from "Guest · Privacy" in the footer. It uses four plain lines and no legal text.
Session endedA thank-you message. It links to the slides only if the presenter shared the deck by link.
Network blocks live updatesWhen even the SSE and long-polling fallbacks fail, or the phone is offline, the page explains and retries. There is no guest cap (D7).
Turn the phone sidewaysIn landscape the slide fills the screen, which helps people far from the projector.
05

On the big screen

There are two places to show the way in: a dedicated join slide for the start of the talk, and an optional join bar on every slide for late arrivals. Both read the live session, so the code is never typed into the deck.

Join slide · layout joinThe QR code is 780 px on the 1920 canvas, far over the 280 px minimum, so it scans from the back row. The short link and code sit beside it, and the joined count rises as people arrive. An agent adds it with add_slide(layout: "join").
Join bar on a content slideThe bar sits bottom right, above the progress bar. It is a deck setting, so the presenter can switch it on mid-talk.
Join slide before Go liveIt renders the deck's standing code (Q4) and shows "Not live yet" instead of a count. In the editor and thumbnails it shows the same.
Rules carried over from an earlier live-poll prototype (SW-1 catalogue §3)
  • The link uses a path (slideworks.live/482913), never a #fragment, which is lost across redirects
  • The short link is printed under the QR for anyone whose camera won't scan
  • The QR is at least 280 px on the canvas, with a quiet zone and error-correction level M
  • The join slide goes early in the talk, and the join bar catches latecomers
  • Guests don't sign in, unlike the prototype, which made voters sign in first
06

Code and link

Joining has its own short domain, slideworks.live, which is easy to say from the stage and short enough to type. The code is easy to read aloud across a room, is typed on a numeric keypad, and is short enough for the QR to stay coarse (a version 3 grid) and scan from the back row.

ChoiceWhy
6 digits, shown 482 913That is a million codes, and only live or standing codes are reserved. It is read out as two triples and typed on a numeric keypad. Mentimeter uses 8 digits because it runs at global scale, and a self-hosted instance doesn't need that (Q1).
no 0-prefix codesThe code runs from 100000 to 999999, so it never starts with a 0 that people drop when they read it out.
slideworks.live/{code}The shortest link possible keeps the QR small. The join domain resolves the code to a session, and a dead code shows the "check the code" state, not a 404.
slideworks.liveThe bare domain is the keypad page, like menti.com. It is all the presenter has to say out loud.
join domain settingAn instance setting seeded by an env var (SLIDEWORKS_JOIN_URL), so SlideWorks stays generic. The hosted instance sets it to https://slideworks.live. When it is unset, links fall back to {instance}/j/{code} and {instance}/join.
rate limitTyped codes are limited to 10 wrong tries a minute per IP, so nobody can walk the code space to drop into other people's talks.
07

Realtime and privacy

SW-1 already ships a SignalR hub (/hubs/deck, WebSockets only) that tells open players a deck changed. SW-5 adds a session group to the same hub. The presenter's player publishes its position, and every guest in the group receives it. This settles the "WebSocket vs SSE" question in the Feature: SignalR, with a fallback for venue Wi-Fi (Q7).

MessageCarries
JoinSession(code)Guest → hub. Returns the current state: deck id, slide, step, activity, ended. A late joiner or a reconnect lands here.
sessionStateHub → guests on every move. The slide index and step only. Guests render the slide from the deck JSON they fetched once.
sessionEndedHub → guests. Shows the ended state and closes the socket.
joinedCountHub → presenter and the join slide, at most once a second.
GoLive / SetPosition / EndPresenter → hub. Only the deck's owner or an editor may call them, the same check as editing.
Privacy model, as the phone states it
  • No account and no name. A guest is a random ID kept in this browser for the session, so a reload doesn't count twice (Q2).
  • The presenter sees totals, never who answered what. That holds for every SW-6+ activity, not just polls.
  • No tracking. The page sets one first-party cookie and loads no analytics or third-party scripts, so it needs no cookie banner.
  • Answers live with the session. Deleting the session or the deck deletes them.
Measures (the Feature said "to confirm")
  • Peak joined per session, against a room size the presenter can type in after the talk
  • Median seconds from the join slide first shown to each join
08

Questions before planning

Answered 17 Nov. Q1–Q6 went as recommended. Q7 uses SignalR with fallbacks and no guest cap. The join domain is slideworks.live. All are recorded as decisions D1–D8 on SW-5.

Q1 · What does the join code look like?

It gets read aloud, typed on a phone and encoded in the QR.

Not queued

Q2 · Does a guest give a name?

Every field on the way in costs joiners. Later features (Q&A, quiz leaderboards) may want a nickname.

Not queued

Q3 · What does the phone show between interactive slides?

The Feature says the phone "follows the presenter's current slide" and "shows a waiting state". This decides whether those are one screen or two.

Not queued

Q4 · How long does a code last?

A code that is known before the talk can go in the invite or on a printed sheet, and the join slide renders correctly in the editor.

Not queued

Q5 · Is the join bar on by default?

It catches latecomers, but it sits on every slide and covers a corner of the canvas.

Not queued

Q6 · Does the room see the joined count?

A rising number on the join slide nudges the room ("23 joined"). Some presenters don't want a low number on screen.

Not queued

Q7 · Realtime transport and limits

The SW-1 hub is WebSockets only. Venue and corporate Wi-Fi sometimes block WebSockets, and phones on 4G switch networks. Answered: the fallbacks, with no cap ("let them in").

Not queued
